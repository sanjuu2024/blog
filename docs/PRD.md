# 个人技术博客系统 PRD

## 1. 文档信息

- 项目名称：个人技术博客系统
- 文档版本：v1.0
- 文档日期：2026-04-22
- 文档状态：初稿

## 2. 产品概述

### 2.1 产品背景

本项目用于个人技术文章沉淀，同时作为 `Vue + Spring Boot + PostgreSQL + Redis` 的全链路练手项目。项目目标不是一次性构建复杂社区，而是在可控范围内完成从前台展示、注册登录、权限控制到后台管理的完整闭环。

### 2.2 产品目标

- 支撑个人技术文章的长期沉淀与展示
- 提供极简个人主页风格的博客体验
- 打通用户注册、登录、鉴权、文章管理、公开浏览的主链路
- 为后续评论、点赞、邮件通知和邮件验证等能力预留扩展空间

### 2.3 产品定位

- 类型：个人技术博客
- 风格：极简个人主页
- 核心特点：轻量、完整、可扩展

### 2.4 设计原则

- 先完成核心主链路，再逐步增加互动能力
- 首版尽量避免复杂社区化设计
- 数据库设计需为后续版本预留扩展字段和表结构
- 权限边界清晰，管理员、用户、游客职责明确

## 3. 角色定义

| 角色 | 定义 | 权限边界 |
| --- | --- | --- |
| 管理员 | 站点拥有者，负责站点运营和内容管理 | 可管理用户、文章、分类、标签，可发布和下线文章 |
| 用户 | 已注册并登录的普通用户 | 可注册、登录、维护个人资料；后续版本可参与互动 |
| 游客 | 未登录访客 | 可浏览公开内容，可发表留言；留言审核通过后公开 |

## 6. 功能范围说明

### 6.1 已确认规则

- 注册方式：用户名 + 邮箱 + 密码
- 登录方式：用户名或邮箱 + 密码
- 文章编辑器：Markdown + 第三方库
- 文章状态：草稿 / 已发布 / 已下线
- 分类采用两级结构：一级分类如 `技术`、`学业`、`消遣`、`杂记`，后续可继续新增；二级分类如 `算法`、`Java`、`前端三剑客`
- 文章必须归属一个二级分类，一级分类通过二级分类的父分类进行归属
- 仅管理员可发文
- 登录用户在 P0 仅比游客多出个人中心与资料修改能力
- 评论、点赞不在 P0 实现，但需在数据层预留
- 被禁用用户不可登录
- 已登录用户若被禁用，已有 Access Token 在下一次请求时通过 tokenVersion 校验立即失效，Refresh Token 刷新必须失败
- 修改密码或用户被禁用后，后端撤销该用户全部活跃 Refresh Token 并递增 tokenVersion；修改角色不撤销 Refresh Token，但同样递增 tokenVersion，新的角色在刷新登录态或重新登录后生效
- 公开用户资料、文章作者信息可以返回用户 ID；公开资料卡以 `userId` 作为路径标识，`username` 作为展示和登录标识

### 6.2 上传能力说明

- P0 不做图片上传服务
- P0 用户头像使用默认头像
- P0 文章封面字段保留，但不提供本地上传能力，后台可先手工录入图片 URL
- P0 文章正文可通过 Markdown 图片语法引用已有图片 URL，但不提供编辑器内上传能力
- P1 使用阿里云 OSS 公共读 Bucket 提供头像、文章封面、文章正文图片和后续项目封面上传能力
- 图片由后端接收并中转上传到 OSS，前端不得持有对象存储 AccessKey；后端负责鉴权、文件校验和对象 key 生成
- 图片使用自定义公开域名访问，数据库和 Markdown 只保存完整 URL，不保存图片二进制，也不新增通用文件资源表
- 支持 JPEG（`.jpg`、`.jpeg`）、PNG、WebP 和 GIF，不支持 SVG；头像最大 2 MB，其他图片最大 10 MB
- P1 保留原始图片，不压缩、不转换格式、不生成缩略图，也不提供头像裁剪；头像展示使用居中覆盖样式
- 所有 OSS 对象使用不可变 UUID key，不覆盖同名对象；P1 替换头像、封面或删除文章时不自动删除旧 OSS 对象
- 同一用户每分钟最多上传 1 次头像，并且每 24 小时最多上传 10 次；后台图片上传仅管理员可用
- 后台文章封面保留手工输入 URL 的能力，同时提供上传按钮；正文编辑器上传成功后自动插入 Markdown 图片语法

## 7. 管理员视角 PRD

### 7.1 用户管理

#### 7.1.1 目标

管理员可以对站内用户进行统一管理，确保账号状态、权限和安全可控。

#### 7.1.2 功能需求

- 查看用户列表
- 按用户名、邮箱、状态、角色筛选用户
- 用户名和邮箱使用两个独立筛选项，均按不区分大小写的字面量包含关系模糊搜索，可以与状态、角色条件组合查询
- 查看用户注册时间、最近登录时间
- 用户列表默认按注册时间倒序展示，同一注册时间下按用户 ID 倒序展示
- 启用用户
- 禁用用户
- 修改用户角色

#### 7.1.3 业务规则

- 被禁用用户不能通过用户名或邮箱登录
- 管理员不能修改当前登录用户自身的状态和角色
- 禁用用户后，后端需撤销该用户全部活跃 Refresh Token；启用用户不需要撤销 Refresh Token
- 修改用户角色后不撤销 Refresh Token；新的角色在刷新登录态或重新登录后生效
- 已登录用户若被禁用或角色被变更，已有 Access Token 在下一次请求时通过 tokenVersion 校验立即失效
- 管理员可将普通用户设置为管理员，但首版默认仅一个管理员使用场景

### 7.2 文章管理

#### 7.2.1 目标

管理员可以完成技术文章从创建到发布、下线的完整生命周期管理。

#### 7.2.2 功能需求

- 新建文章
- 编辑文章
- 删除文章
- 保存草稿
- 发布文章
- 下线文章
- 设置文章二级分类
- 设置文章标签
- 设置文章摘要
- 设置文章封面字段
- 设置文章是否置顶
- 查看发布时间与更新时间

#### 7.2.3 文章编辑字段

- 标题
- 摘要
- Markdown 正文
  说明：系统基于 Markdown 自动生成 HTML 正文与纯文本正文
- 二级分类
- 标签
- 封面
- 置顶状态
- 文章状态

#### 7.2.4 业务规则

- 草稿文章前台不可见
- 已发布文章可在前台展示
- 已下线文章前台不可见
- `DRAFT` 表示从未发布过的草稿；`OFFLINE` 表示曾经发布过但当前下线，不应把已发布过的文章重新转为草稿
- 创建文章时仅允许保存为 `DRAFT` 或 `PUBLISHED`，不允许直接创建为 `OFFLINE`
- 从未发布过的文章可在编辑页继续保存为 `DRAFT`，也可发布为 `PUBLISHED`，不允许转为 `OFFLINE`
- 已发布过的文章仅允许在 `PUBLISHED` 与 `OFFLINE` 之间流转，不允许回退为 `DRAFT`
- `publishedAt` 表示首次发布时间，仅在文章第一次变为 `PUBLISHED` 时写入；下线、重新发布或更新已发布文章时不刷新
- 文章发布前必须绑定一个二级分类
- 管理端以 Markdown 作为文章编辑源
- 后端需根据 Markdown 自动转译并存储 HTML 正文，供前台渲染使用
- 后端需根据 Markdown 自动提取并存储纯文本正文，供后续全文搜索使用
- 置顶文章在列表中排在普通文章之前
- 多篇置顶文章之间按发布时间倒序排列

### 7.3 分类管理

#### 7.3.1 功能需求

- 新增一级分类
- 新增二级分类
- 编辑分类
- 删除分类
- 设置父级分类
- 设置分类层级
- 设置分类描述
- 设置分类排序

#### 7.3.2 业务规则

- 分类采用两级结构
- 一级分类用于内容聚合与前台导航分组
- 二级分类用于文章实际归属
- 一级分类初始默认包含：`技术`、`学业`、`消遣`、`杂记`
- 一级分类后续允许继续新增
- 二级分类必须挂载在某个一级分类下
- 文章只能绑定二级分类，不能直接绑定一级分类

### 7.4 标签管理

#### 7.4.1 功能需求

- 新增标签
- 编辑标签
- 删除标签

#### 7.4.2 业务规则

- 标签不出现在前台主导航
- 标签用于后台配置、文章关联和后续搜索筛选

### 7.5 后台权限控制

#### 7.5.1 功能需求

- 后台页面仅管理员可访问
- 后台接口必须校验管理员角色
- 无权限用户访问后台时应被拒绝并跳转登录或返回无权限提示

### 7.6 操作审计日志

#### 7.6.1 功能需求

- 新增后台操作审计日志查询页面，仅管理员可访问
- 审计日志记录操作者用户 ID、用户名快照、目标资源类型、目标资源标识、操作类型、操作明细、操作结果、失败业务码、请求方法、请求路径和操作时间
- 支持按操作者、资源类型、目标资源标识、操作类型、操作结果和时间范围筛选
- 日志按操作时间倒序、日志 ID 倒序展示
- 审计日志只允许追加和查询，不提供修改或删除接口

#### 7.6.2 业务规则

- 后台新增、更新、删除、状态变更、角色变更、审核、回复、批量通过和图片上传等写操作必须记录审计日志
- 成功操作与成功日志在同一事务中提交；任一方失败时一起回滚
- 业务失败在原事务回滚后以独立事务追加失败日志，保留失败业务码和安全错误说明
- 审计日志不保存请求体、查询参数、密码、Token、邮箱、留言或评论正文、文件原名等敏感内容
- 目标资源标识仅保存路径 ID、返回资源 ID、批量 ID 列表或 OSS 公开 URL 等已声明字段

### 7.7 评论管理

#### 7.7.1 功能需求

- 新增后台评论管理页面，仅管理员可访问
- 管理员可按文章、评论用户、评论状态和创建时间筛选评论
- 管理员可查看待审核、已通过、已拒绝、已隐藏和已删除评论
- 管理员可通过或拒绝待审核评论
- 管理员可隐藏已经公开的评论
- 管理员可删除评论
- 审核、拒绝、隐藏和删除操作需记录操作者、操作时间及可选的处理原因

#### 7.7.2 业务规则

- `PENDING` 表示等待站长审核，`APPROVED` 表示审核通过并可公开展示
- `REJECTED` 表示审核未通过且从未公开，`HIDDEN` 表示曾公开但被管理员隐藏，`DELETED` 表示已逻辑删除
- 管理员不得修改用户发表的评论内容，只能审核、拒绝、隐藏或删除
- 删除评论时，其所有层级的子回复必须在同一事务中一并逻辑删除
- 删除评论子树时，需从文章 `comment_count` 中扣除该子树原有的全部 `APPROVED` 评论数
- 评论状态变化与文章 `comment_count` 更新必须在同一事务中完成
- P1 后台管理操作审计日志需覆盖评论审核、拒绝、隐藏和删除操作

### 7.8 留言管理

#### 7.8.1 功能需求

- 新增 `/messages` 前台留言页，游客和登录用户均可发表顶层留言
- 游客可填写昵称和可选邮箱；勾选回复通知时邮箱必填
- 登录用户可选择使用账号邮箱接收回复通知，并可通过邮件中的链接关闭该条留言的后续通知
- 仅管理员可以回复留言，管理员回复直接通过并可发送回复通知邮件
- 后台可按留言 ID、用户 ID、游客昵称、游客邮箱、内容、状态、层级和创建时间筛选
- 后台支持逐条审核、拒绝、隐藏、删除，以及对待审核顶层留言批量一键通过
- 提供按单条顶层留言退订后续回复通知的页面和接口

#### 7.8.2 业务规则

- 游客留言的 `userId` 为空；之后使用相同邮箱注册的用户不会自动关联历史游客留言
- 普通用户和游客留言初始为 `PENDING`；管理员发表的留言或回复直接为 `APPROVED`
- 留言状态为 `PENDING`、`APPROVED`、`REJECTED`、`HIDDEN`、`DELETED`，`DELETED` 为终态
- 普通用户登录后可看到自己待审核或已拒绝的留言；游客刷新后无法找回未审核留言
- 留言列表和发表接口允许游客不携带 Access Token 访问；请求一旦携带 Token 就必须校验成功，不得把失效登录态静默降级为游客
- 登录用户只能逻辑删除自己的顶层留言；删除顶层留言时其管理员回复一并逻辑删除
- 管理员可回复已通过的顶层留言；已通过留言可隐藏，未删除留言可逻辑删除，但不可编辑内容
- 拒绝、隐藏、删除必须填写处理原因；通过时清空旧原因
- 批量通过只接受待审核顶层留言，最多 100 条，事务内全成功或全失败
- 游客按客户端 IP 限制每 30 秒 1 条、每小时最多 10 条；登录用户按用户 ID使用相同窗口限流
- P1 不在留言表保存原始 IP；反向代理在边缘层另行限流
- 勾选回复通知后保存邮箱和随机退订令牌；P1 每条管理员回复分别发送一封纯文本邮件，P2 升级为同时携带纯文本和 HTML 的 `multipart/alternative` 邮件
- 邮件在事务提交后异步发送，首次尝试失败后按递增间隔最多重试 3 次；只记录留言 ID、尝试次数和异常类型
- 退订链接只关闭该顶层留言的后续通知，GET 页面不修改状态，POST 操作幂等

## 8. 用户视角 PRD

### 8.1 注册

#### 8.1.1 功能需求

- 用户可通过注册页创建账号
- 注册时需填写用户名、邮箱、密码

#### 8.1.2 校验规则

- 用户名不能为空
- 用户名长度为 2-20 个字符，只允许英文字母、数字、下划线和短横线，不限制首字符类型
- 邮箱格式必须合法；注册邮箱仅支持常见邮箱格式，不能包含空格或中文字符
- 用户名唯一性按大小写不敏感处理，但保留注册时输入的原始大小写用于展示。例如允许用户注册展示名 `Sanjuu`，但不允许另一个人再注册 `sanjuu`
- 用户名注册后不可修改
- 邮箱唯一性按大小写不敏感处理；产品层统一将 `A@example.com` 和 `a@example.com` 视为同一个邮箱账号
- 密码长度为 6-32 个字符；允许英文字母、数字、下划线、短横线和常用 ASCII 特殊字符；不允许中文或空白字符
- 注册时无需填写昵称，服务端默认使用用户名初始化昵称

### 8.2 登录

#### 8.2.1 功能需求

- 用户可通过用户名 + 密码登录
- 用户可通过邮箱 + 密码登录
- 登录成功后获取 Access Token；Refresh Token 由后端写入 HttpOnly Cookie
- 登录账号必须符合用户名或邮箱格式；用户名为 2-20 位英文字母、数字、下划线或短横线，包含 `@` 时按邮箱登录，否则按用户名登录
- 用户名和邮箱登录均按大小写不敏感处理。也就是允许用户注册展示名 `Sanjuu`，但不允许另一个人再注册 `sanjuu`；登录时输入 `sanjuu`、`SANJUU`、`Sanjuu` 都能找到同一个账号。邮箱同理，`A@example.com` 和 `a@example.com` 会识别为同一个邮箱账号

#### 8.2.2 业务规则

- Access Token 用于接口访问
- Access Token 有效期较短，P0 默认为 15 分钟
- Refresh Token 用于续期登录态和退出登录，由后端通过 `Set-Cookie` 写入 `refresh_token` HttpOnly Cookie，前端 JavaScript 不读取或持久化 Refresh Token
- `refresh_token` Cookie 路径为 `/api/v1/auth`，只随 `/api/v1/auth/**` 请求发送；开发和生产均按同域请求设计，不依赖 CORS
- P0 阶段 Refresh Token 以数据库会话表做存储与失效控制
- P1 已使用 Redis 缓存 tokenVersion，用于降低鉴权查询成本，并支持权限变化后的旧 Access Token 立即失效；Refresh Token 会话仍以数据库为权威来源
- Access Token 携带登录或刷新时的用户角色、状态快照和 tokenVersion；每次鉴权时与 Redis 或数据库中的当前版本比较
- Refresh Token 使用轮转机制，每次刷新成功后旧 Refresh Token 立即失效，并签发新的 Refresh Token
- P0 阶段 Refresh Token 缺失、格式错误、签名无效、已过期、已撤销或找不到对应会话时，统一视为刷新失败，前端清理本地登录态并引导重新登录
- P0 阶段不因普通刷新失败自动撤销该用户全部活跃 Refresh Token；修改密码、用户禁用、管理员强制下线等明确安全事件可撤销全部会话
- P1 阶段可为刚轮转的旧 Refresh Token 设置短暂宽限期，用于同一次刷新请求的幂等重试；也可结合 Redis 与 tokenVersion 增强重放检测
- 用户退出登录时，Refresh Token 需失效
- 退出登录接口不要求有效 Access Token，后端通过 `refresh_token` Cookie 尝试撤销当前会话；若 Refresh Token 缺失、已过期、已撤销或找不到对应会话，仍视为退出成功，前端清理本地登录态即可

- 修改昵称
- 修改个人简介
- P1 支持上传自定义头像，上传成功后立即更新当前用户头像

#### 8.3.2 暂不支持

### 8.4 内容浏览

#### 8.4.1 功能需求

- 浏览已发布文章列表
- 查看文章详情
- 按一级分类或二级分类查看文章
- 按关键词搜索已发布文章
- 查看文章作者公开资料卡，仅展示用户名、昵称、头像和个人简介等基础信息

#### 8.4.2 搜索规则

- 搜索关键词最长 100 个字符，去除首尾空白后为空时视为未搜索
- 关键词同时匹配文章标题、摘要和由 Markdown 提取的纯文本正文，不匹配 Markdown 标记或 HTML 标签
- 搜索使用 PostgreSQL `zhparser` 中文全文检索；多个解析后的检索词之间为 AND 关系，只返回所属分类及父分类均启用的已发布文章
- 默认搜索结果按全文检索相关度降序排列，相关度相同时按置顶、首次发布时间和文章 ID 倒序排列；显式使用最新排序时仅按首次发布时间和文章 ID 倒序排列
- 当单字符未被 `zhparser` 解析为词元时，标题、摘要和纯文本正文使用字面量包含匹配兜底，避免中文单字搜索为空
- 搜索可以与分类、标签筛选组合使用，结果继续使用文章列表的滚动分页
- 搜索关键词保存在 `/articles` 路由的 `keyword` query 参数中，刷新、分享链接和浏览器前进后退时均可恢复
- 搜索结果展示命中文章总数，并高亮标题中的命中文本
- 摘要命中时展示高亮摘要；摘要未命中但正文命中时，展示正文命中位置附近的高亮片段
- 搜索框固定在页面顶端区域，页面滚动时吸附在全局页头下方；分类和标签筛选位于文章列表页顶部并随页面正常滚动
- P1 不提供输入时自动搜索或独立搜索结果页

#### 8.4.3 后续扩展

- 评论
- 点赞

### 8.5 评论

#### 8.5.1 功能需求

- 登录用户可在允许评论的已发布文章下发表评论
- 登录用户可回复已经审核通过的评论
- 评论作者可删除自己发表的评论，但不可编辑评论内容
- 评论作者可查看自己的待审核和已拒绝评论及对应状态
- 游客和其他普通用户只能查看审核通过的评论

#### 8.5.2 展示规则

- 评论支持无限层级回复关系，数据层保留直接父评论和所属顶层评论
- 前端只展示两层：顶层评论单独展示，其下所有层级回复在第二层平铺
- 平铺回复时仍需展示直接被回复的用户，以保留对话上下文
- 顶层评论采用滚动加载，默认按创建时间倒序排列
- 同一顶层评论下的回复默认按创建时间正序排列
- 顶层评论和回复均只向非作者用户展示 `APPROVED` 状态的数据
- 评论列表和回复列表允许游客不携带 Access Token 访问；请求一旦携带 Token 就必须校验成功，不得把失效登录态静默降级为游客
- 顶层评论默认只展示 APPROVED 回复总数，不预载回复内容；用户点击“共 x 条回复，点击查看”后再展开回复区域。评论作者自己的 PENDING、REJECTED 回复仍可见，但不计入该数量
- 首次展开加载 5 条回复，后续每次加载 10 条，直至展示完全部可见回复；回复区域支持收起

#### 8.5.3 审核与删除规则

- 普通用户新发表评论或回复默认状态为 `PENDING`，审核通过前仅评论作者和管理员可见
- 管理员新发表评论或回复直接创建为 `APPROVED`，无需审核，且不写入 `reviewedBy`、`reviewedAt`
- 站长负责评论审核，审核通过后状态变为 `APPROVED` 并公开展示
- 已拒绝评论仅评论作者和管理员可见，不计入公开评论数
- 用户删除自己的评论时，其所有层级子回复一并逻辑删除
- 管理员可以拒绝、隐藏或删除评论；隐藏和删除后的评论不再公开展示
- `comment_count` 统计文章下全部 `APPROVED` 评论，包括顶层评论和回复，不统计 `PENDING`、`REJECTED`、`HIDDEN`、`DELETED`

#### 8.5.4 内容与频率规则

- P1 评论仅支持纯文本，长度为 1-1000 个字符，去除首尾空白后不得为空
- P1 不解析评论中的 HTML 或 Markdown，前端必须按纯文本安全展示
- P2 再评估自定义表情、图片回复和受限 Markdown/代码内容
- 同一登录用户对同一文章每 10 秒最多发表一条评论或回复
- P1 使用 Redis 原子限流，限流维度为 `userId + articleId`，不依赖浏览器签名
- 被禁用用户不能发表评论或回复
- 文章 `allow_comment = false` 时禁止新增评论和回复，但已有审核通过的评论继续展示，评论作者仍可删除自己的已有评论

#### 8.5.5 P2 评论直接回复邮件通知

- 登录用户发表评论或回复时，可自愿勾选接收该条评论的直接回复通知；使用账号邮箱，不重复填写邮箱
- 只有其他用户对该评论的直接回复变为 `APPROVED` 后才发送通知；`PENDING` 阶段和自己回复自己均不发送
- 通知订阅以当前评论为范围，邮件中的退订链接只关闭该评论未来的直接回复通知
- 评论通知与留言通知统一使用 `multipart/alternative`，同时提供语义一致的 `text/plain` 备用正文和带样式的 `text/html` 正文
- HTML 正文可展示文章标题、原评论、直接回复和查看链接；所有用户内容必须经过 HTML 转义

### 8.6 留言

#### 8.6.1 展示与交互

## 11. 核心业务流程

### 11.1 注册流程

1. 用户进入注册页
2. 输入用户名、邮箱、密码
3. 前端进行基础校验
4. 后端校验用户名和邮箱唯一性
5. 注册成功后跳转登录页

### 11.2 登录流程

1. 用户输入用户名或邮箱，以及密码
2. 后端锁定用户记录，并基于最新账号状态和密码完成校验
3. 登录成功后签发 Access Token 和 Refresh Token
4. P0 阶段 Refresh Token 写入数据库会话表，并通过 `Set-Cookie` 写入 `refresh_token` HttpOnly Cookie；P1 阶段可同步写入 Redis 运行态会话
5. 前端保存 Access Token，使用 Access Token 访问受保护接口

### 11.3 刷新登录态流程

1. Access Token 过期
2. 前端请求刷新登录态接口，浏览器自动携带 `refresh_token` Cookie
3. 后端校验 Refresh Token 是否存在、是否过期、用户是否被禁用
4. 校验通过则签发新的 Access Token 和新的 Refresh Token，并通过 `Set-Cookie` 轮转 `refresh_token` Cookie
5. 后端将本次请求携带的旧 Refresh Token 标记为失效
6. 若刷新失败，P0 阶段统一要求前端清理本地登录态并重新登录；P1 阶段可结合 Redis 宽限期处理幂等重试

### 11.4 退出登录流程

1. 用户发起退出登录
2. 浏览器自动携带 `refresh_token` Cookie，后端尝试使当前 Refresh Token 失效；无需先刷新 Access Token，若 Refresh Token 缺失、已过期、已撤销或找不到对应会话，仍返回退出成功
3. 前端清理本地登录态
4. 后端通过 `Set-Cookie` 清除 `refresh_token` Cookie
5. 跳转到首页或登录页

### 11.5 文章发布流程

1. 管理员进入文章新建页
2. 输入标题、摘要、正文、分类、标签等内容
3. 可先保存为草稿
4. 确认内容后发布文章
5. 发布后的文章出现在前台列表
6. 如需撤回展示，可将文章下线

### 11.6 用户禁用流程

1. 管理员在后台禁用指定用户
2. 被禁用用户无法再次登录
3. 后端撤销该用户全部活跃 Refresh Token
4. 后端原子递增该用户的 tokenVersion
5. 该用户已有 Access Token 在下一次请求时因版本不一致立即失效

### 11.7 留言提交与回复通知流程

1. 游客或登录用户提交顶层留言；后端校验内容、邮箱、文章外的留言规则并通过 Redis 原子限流
2. 普通留言写入 `PENDING`；管理员留言写入 `APPROVED`
3. 管理员在后台审核，或使用批量通过处理待审核顶层留言
4. 管理员对已通过留言发表回复；事务提交后异步读取收件地址和退订令牌发送 P1 纯文本通知
5. 邮件失败时按 2 秒、10 秒、30 秒间隔重试；邮件发送器不可用或重试最终失败时，仅写入不包含正文和邮箱的错误日志，不回滚已提交的管理员回复
6. 收件人访问退订页并提交退订后，后续回复不再触发通知，已有邮件不受影响
7. P2 将留言通知与评论直接回复通知统一升级为 `multipart/alternative`，HTML 版本用于样式展示，纯文本版本用于兼容和降级

- `status`
- `reviewed_by`
- `reviewed_at`

- `created_at`
- `updated_at`

### 13.9 历史收藏结构说明

早期版本的 `V1.0.0` migration 已创建 `blog_article_favorite` 表和文章表中的
`favorite_count` 字段。收藏功能当前暂不排期，应用接口、响应和页面不使用这些结构；
由于历史 migration 已执行，不修改或回滚该表和字段。未来是否启用收藏，待文章规模和
用户复访需求明确后重新评估。

## 15. P0 验收标准

- 游客可以浏览已发布文章与分类内容
- 用户可以完成注册、登录、退出和刷新登录态
- 管理员可以完成用户管理、文章管理、分类管理、标签管理
- 文章支持草稿、已发布、已下线三种状态
- 前台仅展示已发布文章
- 标签不出现在主导航中
- 被禁用用户不能登录，已有会话在刷新时失效
- 数据结构已为评论、点赞、邮箱验证等后续能力预留扩展空间；历史数据库仍保留未启用的收藏结构
